# 重构代码

让现有代码更容易理解、修改和验证。优先清晰直接的实现，而不是更少的行数、更多的文件或更复杂的架构。

## 确定范围

- 读取适用的 AGENTS.md，遵守项目语言、框架和既有风格。
- 优先处理用户指定的范围；未指定时，处理当前任务中最近修改的代码。两者都不明确时先询问。
- 只检查目标代码及必要的调用者、依赖和测试，跳过第三方代码、生成文件和构建产物。
- 用户只要求分析或方案时保持只读；要求重构时，小范围修改可直接推进，跨模块职责或公共接口调整先确认方案。
- 保留已有未提交修改，不自动提交或推送。

## 理解与规划

修改前确认代码的职责、数据流、外部接口和重要副作用，避免只根据局部写法判断冗余。

选择最影响理解和维护的问题，简要说明准备调整什么、为什么以及如何验证。小任务不必输出长篇报告；大范围任务分批处理。

## 重构原则

优先考虑：

- 改善含糊或误导性的命名；
- 按完整职责拆分过长函数和职责混杂的类；
- 减少不必要的嵌套，简化条件和控制流；
- 合并语义相同、变化原因一致的重复逻辑；
- 删除确认无用的代码、变量、注释和中间层；
- 将相关逻辑放在一起，减少跨文件跳转和隐式依赖。

保持克制：

- 不为了减少行数使用密集表达式、嵌套三元或晦涩技巧。
- 不机械限制函数行数，不把连续逻辑拆成大量碎片。
- 不因代码长得相似就强行抽象，也不为假设中的未来需求搭建框架。
- 只有能明确降低当前复杂度时，才引入接口、基类或设计模式。
- 已经清晰的代码保持不变，不顺手进行全项目格式化。
- 注释只解释不明显的原因和约束，能一句说清楚就不用两句，遵循目标语言的有效语法。

## 行为边界

重构不混入新功能、算法替换或缺陷修复；发现问题单独说明。

保持外部接口、返回值、异常语义、数据格式和重要副作用不变。涉及数值、实时或并发代码时，特别检查精度、单位、时序、状态更新顺序和线程行为。

删除或重命名前检查引用，也考虑反射、配置、序列化和动态加载；不能仅凭搜索不到调用就判定无用。

## 执行与验证

- 先运行相关现有检查，记录基线，区分原有失败和新引入的问题。
- 缺少测试时，优先为将要改变结构的关键行为补充最小回归测试、固定样例或输入输出回放。
- 每批只处理一种清晰的结构问题，完成后运行对应测试或检查。
- 优先使用项目已有测试和工具，不为普通整理额外引入依赖。
- 若无法验证关键行为，停止高风险修改，说明缺口；不要把编译通过等同于行为一致。
- 检查最终 diff，确认修改没有超出范围，调用关系更清晰，并且没有引入明显性能退化。

## 完成说明

简要说明调整了哪些职责或结构、为什么更容易理解、执行了哪些验证，以及仍未验证的风险。

没有值得改的地方时直接说明，不为产生修改而重构。
