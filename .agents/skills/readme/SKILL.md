# 维护项目 README

根据项目真实内容创建或更新准确、简洁、可执行的 README。

## 定位项目

1. 如果用户指定了项目路径，优先使用该路径。
2. 否则尝试使用当前 Git 仓库根目录。
3. 如果当前目录不是 Git 仓库：
   - 工作区内只有一个仓库时，使用该仓库；
   - 存在多个仓库时，让用户选择；
   - 没有 Git 仓库时，将当前目录作为项目根目录。
4. 读取适用的 `AGENTS.md`。
5. 默认维护项目根目录中的 README。

不要根据文件夹名称猜测项目类型、用途或技术栈。

## 调研项目

优先检查：

- 已有的 `README` 和主要设计文档；
- 项目清单、依赖文件和包管理配置；
- 源码入口和核心模块；
- 构建、运行、测试和部署脚本；
- 配置示例和环境变量说明；
- CI 配置、许可证和贡献规范；
- `docs/` 中的索引或概览文档。

使用 `rg --files` 或等效方式进行针对性检查。

默认排除：

- `.git`；
- `bin`、`obj`、`build`、`dist`；
- 日志、缓存和编译产物；
- 第三方依赖目录；
- 与 README 无关的大型数据和生成文件。

避免为了维护 README 扫描整个大型仓库。

## 确定修改范围

优先更新现有 README，保留仍然准确的内容和既有写作风格。

只有不存在 README 时才创建新文件。

默认沿用已有文件名和主要语言。没有现有约定时，使用用户当前使用的语言。

除非用户明确要求，不创建多语言版本，也不修改 README 以外的文件。

复杂架构、接口和设计决策应链接到专门文档，不要全部复制进 README。

## 组织内容

根据项目实际情况选择必要章节，不强制套用完整模板。可以包括：

1. 项目名称和一句话说明；
2. 当前能力和适用范围；
3. 快速开始；
4. 环境与依赖；
5. 构建、运行和测试；
6. 项目结构或架构概览；
7. 配置与部署；
8. 已知限制和故障排查；
9. 贡献方式和许可证。

把最常用、最可靠的使用路径放在前面。

只在确实能够帮助理解时使用表格、目录树或 Mermaid 图。

不要把 README 写成完整源码清单或冗长设计文档。

## 保证准确

所有说明必须来自代码、配置、脚本、测试或现有文档。

命令必须能够在项目中找到依据，不得编造安装、构建、启动、测试、部署或硬件操作。

明确区分：

- 已验证可用；
- 根据配置推断；
- 尚未验证。

不要把编译成功描述成运行成功、部署成功或实机验证成功。

不要编造版本、兼容平台、性能指标、维护状态或许可证。

不要写入密码、令牌、私有地址、个人绝对路径或其他敏感信息。

信息不足时优先省略非必要内容；必要信息缺失时标记为“待确认”。

## 验证结果

完成后：

- 检查 README 中引用的文件和相对路径真实存在；
- 检查示例命令与项目文件保持一致；
- 安全且成本较低时，验证最关键的构建或测试命令；
- 未执行的命令必须明确说明；
- 检查最终 diff，避免无关重写、重复章节和格式噪声；
- 确认默认只修改了目标 README。

最后报告修改的 README、主要新增或修正内容、执行的验证和仍待确认的信息。
