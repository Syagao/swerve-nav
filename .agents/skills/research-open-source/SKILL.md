# 调研开源实现

在修改当前项目之前，查找值得参考的开源实现并给出适配建议。保持调研范围聚焦，默认不执行实现。

## 明确目标

1. 读取适用的 `AGENTS.md` 以及与目标功能直接相关的少量代码、配置或文档。
2. 确认目标功能、语言、框架、运行平台、性能要求和不可改变的约束。
3. 信息不足但不影响初步调研时，明确假设后继续；会显著改变搜索方向时再向用户确认。

## 搜索与筛选

1. 优先搜索 GitHub 项目、项目官方文档和原始论文；技术事实优先采用一手来源。
2. 使用功能名称、算法名称、语言、框架和平台组合关键词，必要时补充英文同义词。
3. 先广泛发现候选，再选出最多 3 个最有参考价值的实现进行深入检查，避免扫描整个仓库。
4. 对候选项目检查：
   - 是否存在真实实现，而不只是示例、包装或宣传；
   - 关键文件、类、函数及其调用方式；
   - 最近维护情况、版本和已知问题；
   - 测试、文档和工程完整性；
   - 依赖、平台、数据结构、接口、单位和坐标系兼容性；
   - 许可证及复制、修改、分发时的义务。
5. Star 数只能作为辅助信号，不得替代代码质量和适配性判断。

如果当前环境不能联网或搜索，应明确说明限制，不得假装已经完成 GitHub 调研。

## 对照当前项目

对每个候选实现说明：

- 可以借鉴的算法、结构或工程处理方式；
- 与当前项目不兼容或需要改造的部分；
- 引入依赖、许可证、维护性和性能方面的风险；
- 推荐“直接使用依赖、局部适配、理解后重写”中的哪种方式及原因。

如果当前项目已经存在等价能力，应优先指出并评估复用现有实现，不要为了使用开源方案重复开发。

## 输出结果

结果保持简洁并包含：

1. 调研目标和当前约束；
2. 最多3个候选项目的链接和核心实现位置；
3. 实现思路、维护状态、许可证和适配性比较；
4. 推荐方案、选择原因和不推荐方案的主要问题；
5. 建议的最小落地步骤以及仍待确认的信息。

明确区分已从源码或官方资料确认的事实、合理推断和未验证信息。所有关键结论尽量附上可访问的来源链接或仓库路径。

## 安全限制

- 默认只读，不修改当前项目、参考项目、配置或知识库。
- 未经用户明确同意，不克隆仓库、不安装依赖、不运行外部代码。
- 不直接复制大段开源代码；必须先确认许可证并评估兼容性。
- 不提交、推送或创建 PR。
- 不扩大到与目标无关的全仓库调研。
- 用户要求继续实现时，先概括拟采用的方案和影响范围，再进入相应开发流程。
